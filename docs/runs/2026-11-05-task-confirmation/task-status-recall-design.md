# Typed task-status recall implementation plan

**Status:** Design only. Part A owns task-completion authorization and the explicit confirmation event. Part B consumes its reviewed event contract. Ordinary natural-language recall and P1 acceptance remain open.

**Goal:** Answer a bounded class of questions about the current status of a uniquely identified saved task using the actual task and history stores.

**Architecture:** An authenticated conversation can return a local, typed task-status view alongside the existing source and claim answer paths. The persisted assistant turn contains only a versioned reference. Conversation readback checks that reference before rendering. The task stays in the existing TaskStore.

**Scope:** [Part B requirements](task-completion-recall-brief.md) and [HTTP reproduction](task-completion-recall-report.md). Implement through the existing TaskStore, conversation routes and React task detail. Use the existing test-first and review workflow. No production or test edits were made during design.

## What the current interfaces can establish

| Interface | Reuse | Limit |
| --- | --- | --- |
| `TaskStore.get` and `task_events(task_id, sequence)` | Indexed task ID and history reads. Task writes and their event share a transaction. Title edits append an event without storing title text. | `get` and `history` are separate snapshots. Public history takes the newest 100 events. Generic `completed` and migrated snapshots have unknown actor. |
| `TaskStore.page` and `task_pages.query_page` | Existing SQLite casefold predicate, parameterized literal filtering and bounded result pages. | Searches title, notes and waiting name by substring. The three views split open/waiting/done and omit dropped. A hit in notes does not identify a task. |
| `frage.Anfrage`, `lexical.terms_v1`, `word_forms`, and `working_memory_words` | Existing lexical candidates and spelling support are available for future local disambiguation. `Anfrage` distinguishes literal search terms from model expansions. | The query model has no typed task target or completion intent. Terms and German noun expansions are retrieval hints. They cannot identify the task, and short pieces of record codes are lost. The mail matching helpers also require thread/person context. |
| Task provenance and `EpisodeStore.belegbarer_snapshot` | Provenance links task creation to a concrete episode. `belegbarer_snapshot` checks active source head, correction and attachment parent. A bounded snapshot supplies a generation-sensitive `support_fingerprint()`. | Provenance identifies how the task was created. It does not prove who closed it or make its title safe to repeat after withdrawal. A user-accepted mail candidate still retains source lineage. |

A read-only probe used an isolated temporary TaskStore with 503 synthetic tasks. The oldest `Atlas Wartung` was done, and a same-title task was dropped. `all_tasks()` missed the older task. The three `page(q='Atlas Wartung')` views combined gave one match. An all-status title predicate with `LIMIT 2` returned both. For `Wurde LINDENBOGEN-46 Materialliste prüfen erledigt?`, `frage.rueckfall` returned `fakt` and the subject `LINDENBOGEN-46 Materialliste`, omitting the task title's action word. `terms_v1` dropped the two-digit code suffix. For `Habe ich die Materialliste für LINDENBOGEN-46 schon geprüft?`, the fallback split subject and case code and provided no binding to the saved title. No model, network, personal store or frozen fixture was used.

## Supported question and identity contract

A small shared parser in `sidecar/icarus_memory/task_status_answers.py` recognizes a single affirmative completion or explicit task-status question. It extracts a literal operand from forms such as `Ist Atlas Wartung erledigt?`, `Habe ich die Aufgabe Atlas Wartung schon abgeschlossen?`, `Wurde „Atlas Wartung“ erledigt?` and `Wie ist der Status der Aufgabe t-…?`. The explicit task form allows a saved ID. The parser does not interpret a timestamp, negation, pronoun, second clause, project overview or command as a task-status request. Apply this path only to a new ordinary turn. Existing procedure choices, evidence choices and literal source requests retain their meaning.

- **ID:** Point lookup of a validated existing ID. An exact ID can resolve tasks with duplicate names. Restrict syntax to the task ID forms created by the store, including suggestion IDs, with a length bound. Do not treat a case number as a task ID.
- **Quoted title:** Match the entire normalized title across all task states. Normalize NFC, case and whitespace. Preserve punctuation, numbers, accents and token order. Two exact title matches require disambiguation even if one is dropped or source-ineligible.
- **Unquoted title:** Use the same full-title match for the literal operand in the recognized question. Also check for literal, token-boundary title extensions of that operand. An extension or a second exact match makes the short reference ambiguous. A single partial, inflected, synonym or suffix hit can prompt the user to specify the task. It cannot authorize a status answer. A near title with the same topic and a different stated action stays a different task. Keep any grammar variants for a leading article explicit and count matches across variants before choosing.
- **Coverage:** Add a private all-state title lookup to TaskStore, modeled on the parameterized SQL in `task_pages.py`. Register one deterministic Unicode-normalizing predicate. Use a small length limit on the query, a SQLite step budget with the progress handler removed in `finally`, and stop at two distinct candidates. Return `unique`, `ambiguous`, `not_found` or `coverage_limited`. A budget stop after one hit never proves uniqueness. ID lookups bypass the title scan. A new title index can be evaluated if real local sizes make the bounded scan impractical. V1 needs neither a new full-text store nor a task-table migration.
- **Routing:** A request with an explicit task marker, explicit ID or quoted title stays on the local status path even if absent, ambiguous or withheld. For an unmarked generic completion question, use the typed path when task lookup produces a candidate, ambiguity or a coverage limit. A completed no-hit search may leave the ordinary source path intact. It passes no saved task data to that path. No candidate title or ID is emitted in ambiguity or withheld messages. A missing match never says the work was never done.

The initial unquoted path handles naturally phrased questions that retain the actual task title. It does not resolve action paraphrases such as `Habe ich die Materialliste für LINDENBOGEN-46 schon geprüft?` against `LINDENBOGEN-46 Materialliste prüfen`. This is a remaining acceptance case. Later work can use existing lexical candidates to ask the user to choose a concrete task before displaying state. A completion-status decision must never be based on a model match score.

## Read and proof contracts

**Store interface:** Add a read-only `TaskStore.status_for_recall(reference)` and a point-ID variant for readback in `tasks.py`. A single read snapshot under the store lock covers the title/ID match, task row and necessary events. It returns a narrow internal projection with ID, title, task state, latest per-task event sequence, active completion transition and eligible explicit confirmation event. It also returns the creation episode reference and, only when relevant, the completion-source episode ID. Use the same connection and a read transaction so another TaskStore instance cannot mix a new task row with older events. Return selected fields instead of a full Task document or a history page.

Use the indexed per-task event order to find the latest active completion boundary, and look for the approved Part A confirmation event within that active interval. Read at most a small number of event rows into Python. Bound the SQL scan and mark unknown if the relevant event cannot be checked. Status changes, reopens, drops, removals and restores are boundaries. An explicitly confirmed transition can start the interval. A later explicit confirmation of an already-done task can belong to that same interval if Part A's contract permits it. A generic completed event or `preexisting_snapshot` cannot establish explicit confirmation. Never identify the active interval by `done_at` equality alone. Two distinct completions can share one time. The latest task event sequence also invalidates a saved view after a title edit, even if the before/after snapshots omit title.

| Saved task state | What the local view may say |
| --- | --- |
| Open | The saved task is open. |
| Dropped | The saved task was dropped. Do not use its `done_at` as completion time. Use a known drop event time only if needed. |
| Done with generic or missing historical origin | Kingfisher records the task as done. Show a known saved completion time and state that confirmation provenance is unknown when relevant. |
| Done with active explicit confirmation | Kingfisher recorded an explicit confirmation for this task. Show `confirmed_at` from the confirmation event separately if it differs from the stored completion time. Keep `actor_id` unknown unless the store actually authenticates it. |
| Done with active `post_completed` | The saved completion is linked to a mail. The current code can reach this event through acceptance of a mail proposal, but the event does not carry the new independent confirmation receipt. Its business time can be mail time. Do not relabel that time as the confirmation time. A mail proposal that is merely pending never changes task state. |

The original task timestamp, event recording timestamp and source timestamp stay distinct. Use the existing timezone-aware human formatter and omit any unknown time. A source report stays available through the source path and cannot change the typed task response. V1 does not compose a joint mail-and-task narrative in the same answer.

**Source support:** For tasks whose creation provenance is an `episode:` reference, require a current `belegbarer_snapshot` plus non-archived state before exposing the saved title in recall. Persist a bounded support fingerprint, never title or quote. Check a second stamp when an active mail-linked completion supplies the displayed basis. Only use `erledigt_grund.episode_id` for a history-backed mail origin because an older reason can survive a reopen or a different completion. Use the existing source size budget and fail closed on a missing, replaced, ignored, archived or inconsistent source. A withheld matching task remains a potential match and cannot be silently filtered out in favor of another task. Source withdrawal does not remove the saved task or rewrite its history. Manual tasks without linked sources use task proof alone. A direct user decision about an episode-linked task still belongs to the user, but V1 withholds the recall view if its linked title cannot safely be displayed. A redacted view of that independent decision can be designed separately.

**Persisted version 1 reference:** `context.task_status_answer` holds a minimal record like `{version: 1, task_id, task_revision, state_event_sequence, confirmation_event_sequence, source_refs: [{episode_id, fingerprint}]}`. The task revision is the latest per-task event sequence, while receipt sequences are independently optional. Require the actual source refs discovered from the task read to match the stored set, with a maximum of two. Use neutral text for persistence, `items=[]`, `answer_mode='memory_evidence'`, `history_egress='local_only'`, `model_called=false`, and no selected claim IDs. Non-resolved responses store a typed generic status with no task ref. Do not persist the rendered title, dates, task fields, source material, task link or repeated user question.

**Readback:** `task_status_answers.project_message` validates the strict record shape, rereads the task by ID and checks its exact revision, active receipt sequences and all source stamps. Reread task revision after source checks to avoid using a torn snapshot across stores. Reuse the server conversation lock where source mutation already uses it. A bounded number of the most recent typed responses are reprojected on a conversation GET. Older or invalid references return generic text, no task link and no stale task fields in either per-message or top-level context. The active reference never follows a later transition or a new source head. Once saved, identity is bound to that concrete ID. A later duplicate title affects fresh matching without redirecting the older answer. Rendering is read-only and provider-free.

## Implementation sequence and tests

1. **Store snapshot and matching.** Add the narrowly scoped reads in `sidecar/icarus_memory/tasks.py` and the reference parser in `task_status_answers.py`. Test with actual synthetic TaskStores in `sidecar/tests/test_task_status_recall.py`. Include an old exact match beyond 500 tasks, a dropped same-title duplicate, an unquoted full title, different same-topic actions, literal punctuation/code boundaries, unsupported paraphrases, an interrupted SQLite scan with one hit and repeated search after interruption. Check current task and active-event reads across more than 100 unrelated edits, and verify the reviewed Part A event with a later reopen and same-timestamp recompletion. No migration, backfill or real model is needed.
2. **Authenticated conversation integration.** In `server.py`, invoke the shared task-status path after command/choice checks and before auto mode calls the question model. Reuse it in the explicit memory conversation and retry paths. Keep it outside `EvidenceAnswer`, normal tool schemas and MCP methods. In `conversations.py`, save neutral content and explicitly protect the typed turn in previews and search. In `server.py`, project the latest bounded typed turns with the same validation used on the POST response, and ensure that top-level context uses the projected result. Omit typed replies from both normal and retry history assembly, with a defensive check in `Agent.load_history`. Mark the corresponding typed lookup user turn so normal and retry model history omit it too. Its existing lookup-only source tag prevents background task extraction. The user-authored question remains in the local conversation. Do not add a new task tool, agent memory, provider schema or Cloud evidence row.
3. **HTTP regression and egress.** Use `create_app` plus an in-process client and synthetic provider. Accept a candidate from a synthetic mail, add an older partial-progress report and use the real direct confirmation action under the clock. Assert that auto and explicit evidence mode show the same ID-bound task state without model input. Explicit literal source lookup still gives the older report as a report. Test actor-unknown legacy and generic tool completions, pending proposals, mail-linked completion with separate time, ambiguity, reopen, drop, source replacement, ignore/re-admit, archive, attachment parent withdrawal, and neutralized top-level context, previews and search. Test read-only GET after mutations and after restart, and compare tasks/history/claims/proposal counts around lookup. Verify that a subsequent local chat, a synthetic external chat and retry contain neither the task answer nor its typed lookup metadata. Test with an enabled synthetic MCP door as well as its default closed configuration to establish that this path adds no task-status tool or answer exposure. Keep tests independent of live models and personal stores.
4. **Inspectable link.** Add a typed `task_link` to conversation message context in `app/kingfisher/src/api.ts`. Use `taskWorkflow.ts::taskHref` from the existing conversation renderer in `App.tsx`, with server-validated ID/state and plain text. Label it `Aufgabe und Verlauf ansehen`. Existing task detail can show History for open and done. `TaskDetail.tsx` currently bypasses `TaskHistory` on its dropped branch, so expose the same history control there if dropped answers carry this label. A history event that has scrolled beyond the 100-entry API window needs an exact read to make a cited event inspectable. Prefer an optional authenticated, task-scoped `sequence` argument on the existing history route, backed by `WHERE task_id=? AND sequence=?` and tested for mismatched IDs. Open or highlight the selected receipt in the existing task detail through a bounded deep-link parameter. If the first patch only links to task detail, label it `Aufgabe ansehen` and record the older-receipt inspection gap. Test current, withdrawn and dropped link rendering, one real deep-link target, and older receipt inspection without listing all events.

Part B depends on the reviewed Part A event shape. The implementation must distinguish what the task store reports now, what an explicit event confirms, and what a historical source said. The remaining work includes paraphrase disambiguation, mixed task/source questions and the actual P1 holdout quality run.
