# Geänderte Quellen zeitnah erneut auf Aufgaben prüfen

Laufzeitcode **634071e91d55cf5360950798cdf6ebe6cd6aebeb**, korrigierte Prüfverträge **fccd5360bd3d10e4ef71fd0d68262c41c761589e**. Baut auf [#47](https://github.com/Icarus-health/kingfisher-app/pull/47) auf; keine Installation oder Veränderung persönlicher Daten.

## Problem und Verhalten

Nach einer Kontaktkorrektur konnte eine bereits bearbeitete Quelle hinter dem persistenten Scan-Cursor bis zum Ende eines großen Erstimports auf erneute Aufgabenprüfung warten. Auch ein früheres leeres Ergebnis wird zwar entwertet, muss aber zeitnah erneut angesehen werden.

Schema 21 ergänzt eine dauerhafte textfreie Wiedervorlage: Quellen-ID, Generation und Position. Der Generationswechsel und Einreihen teilen dieselbe SQLite-Transaktion. Mehrere Änderungen derselben Quelle bündeln sich, ohne ihre Position nach hinten zu schieben. Die Aufgabenprüfung gibt höchstens die Hälfte ihres Modellbudgets an Korrekturen; bei Budget 1 wechseln normale Aufnahme und Korrektur dauerhaft über Neustarts. Fehler und Teiljobs rotieren. Eine Queue-Seite hat maximal 20 Einträge; es wird kein alter Komplettbestand zur Auswahl in Python geladen.

Quellen-/Kontextprüfung und Vorschlagsstatus bleiben erhalten. Erst ein exakt abgeschlossener Kontextjob darf die passende Generation quittieren; globale laufende Lease, Teiljob oder Fehler sind kein Abschluss. Nach einem Crash zwischen Jobcommit und Quittieren wird der gespeicherte Abschluss erkannt, ohne erneuten Modellaufruf. Eine neuere Änderung bleibt durch den Generationsvergleich erhalten. Ausgeschlossene/ungültige Rohquellen werden ohne Auswertung aus der Wiedervorlage genommen. Ausdrückliches Wiederöffnen erhöht die Generation in derselben Episode-Transaktion und reiht neu ein. Modelle werden nie aktiviert; die bestehende lokale Aufgabenprüfung muss ausdrücklich verfügbar/freigegeben sein. Originale und bestätigte Aufgaben bleiben erhalten; keine automatisch bestätigten Fakten oder neuen Außenaktionen.

- 15 neue Fälle zu Priorität hinter großem Backlog, Neustart, deaktivierter Verarbeitung, Bündelung/alter Quittierung, Transaktionsrollback, v20→v21-Erhalt, Fairness bei Fehler/Budget 1, fremder Live-Lease, Crash nach Jobcommit, Fehlerrotation, Teiljobs, Änderung während Prüfung, Seitenbegrenzung/Entzug und Wiederöffnen. Erste drei Verzögerungsfälle auf vorherigem Verhalten rot; Review fand Reopen-Lücke, separat rot bestätigt und korrigiert.
- 199 gezielte Backendfälle bestanden. Enges unabhängiges Design-/Codereview, nach Reopen-Korrektur kein weiterer konkreter Fehler im geprüften Bereich. Reviewer selbst führte keine Tests aus.
- Vollbackend auf sauberem Gitarchiv des Laufzeitcommits (mit isolierter Git-Metadatenhülle für den Repository-Lint): **5913 bestanden, 13 fehlgeschlagen, 1 Plattformskip, 26 Unterfälle bestanden**. Diese Prüfaufbauten/Erwartungen sind korrigiert, ohne Produktionscode zu ändern oder Migrations-/Erhaltungsprüfung zu lockern. **Alle betroffenen Dateisuiten anschließend vollständig bestanden: 53 + 59 = 112 Fälle**.
