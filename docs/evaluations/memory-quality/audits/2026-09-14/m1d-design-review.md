# M1d independent concrete design review

**Conditional approval: incorporate corrections 1–3 before implementation.** Read the concrete design, M1d plan and copied design/review audits against current ProposalStore, EpisodeStore, SelfModelStore/backend, Consolidator and Agent construction surfaces. No production edits, tests, model calls or subagents.

## Required corrections

### 1. Make commitment import isolation an enforceable storage/API rule

A strict parser and the label “application-owned” do not distinguish a locally issued commitment from a well-formed imported one. Current ProposalStore._put serializes an entire Proposal document via UPSERT. Extending Proposal.to_dict/_from_row with an authorization field and allowing generic _put/import to round-trip that field would let imported accepted producer+typed support manufacture the exact matching proof the resolver expects.

Specify separate trusted issuance and untrusted import/write paths. Generic proposal create/import/_put must reject supplied authorization or preserve the existing authoritative commitment without taking the caller's value; generic accept must not issue it. Only the dedicated acceptance/reassessment operation may create/replace it after its checks. A dedicated relational authorization column on the existing producer, maintained by the narrow operation and checked against any serialized mirror, is one implementable choice; sanitizing every generic import/write boundary with a dedicated trusted mutation is another. Neither hashes nor operation/authorized_at strings are authorization. No migration backfill may create a commitment. An imported assertion+proposal into an empty local store must remain unverified even if both contain mutually consistent fabricated commitment fields. Import over an existing producer must not replace its local commitment. Matching copied support against a genuinely existing local commitment is a distinct permitted case only if exact assertion identity/content and every current source check hold. Raw arbitrary database-file replacement remains the separate restore boundary, not something ordinary JSON import should emulate.

Required negatives: pending and accepted generic Proposal import with forged commitment; generic accept with supplied commitment; existing-producer overwrite; copied proof to another root; legacy migration; stripped/unknown/malformed fields fail without creating authority.

### 2. Serialize acceptance before record() can produce domain side effects

Design §5 creates the assertion before the transactional pending recheck. Existing SelfModelStore.record also supersedes old assertions immediately. Two connections can therefore both create children and mutate old superseded_by, while only one later wins proposal acceptance. The loser is not merely a harmless orphan: it can leave a previous valid assertion superseded by an unusable orphan and break the winner's reciprocal correspondence. A final support check does not undo this damage.

Reserve/serialize the exact pending producer before any assertion creation/supersession. Smallest option: a proposal BEGIN IMMEDIATE transaction containing pending/evidence read and the single ASSERTION acceptance attempt, with an explicit transaction-aware final write rather than nested committing _put; reject/accept competitors must use the same transactional pending check. Alternatively persist a narrowly defined accepting reservation and recovery semantics. Establish one lock order across proposal and assertion/source operations. Do not keep an HTTP-only mutex as the concurrency guarantee. Explicitly document what happens if assertion creation has occurred but producer publication fails: retained content may be non-usable, but preexisting supersession changes cannot be described as rolled back. Test two real connections accepting the same superseding proposal, acceptance vs rejection, and failure immediately after record; assert existing supersession links and winner correspondence, not merely one accepted producer.

### 3. Decide audit failure semantics before commitment publication

The current “if audit is required” choice is unresolved. Returning failure after writing a usable authorization is not fail-closed. Choose an explicit contract: the durable producer commitment itself is the authorization record, with subsequent audit append failure reported as an audit limitation (not a denied/rolled-back approval); or require a durable audit decision/intent record before publishing the commitment and distinguish intent from completed reassessment. If separate audit success is mandatory for authorization, resolver eligibility must not accept a commitment lacking that prerequisite. No cross-database atomicity claim. Tests must show the exact usable/non-usable state on audit failure and preserve an honest response. No source text in audit.

## Approved choices and concrete rulings

- **Bounds:** approve16 total evidence entries (count each distinct quote, even on the same source),4096 characters per quote,128 distinct combined producer/source nodes per build plus128 SelfModel nodes,256 outstanding10-minute tokens, list25/default50/max. Reject whole oversized evidence; do not approve a truncated display. Also bound identifier length consistently with existing ID contracts and serialized token-binding size. Expired tokens must be evicted; restart may invalidate tokens. Scan budget and cursor must be explicit so blocked entries cannot cause unbounded search or false completion.
- **Commitment hash:** freeze an explicit immutable field allowlist consistent with ensure_content_unchanged, including ID, kind, statement, original provenance and immutable semantic structure/derivation/supersession inputs. Do not use “full assertion except support” as the authorization identity: confirm/status/last_confirmed_at would otherwise permanently break legitimate support. Preview binds the full current assertion, and normal M1c history hashes/live privacy/state/currency remain stricter. Include approved producer evidence and support hash independently. Redaction clears quotes and prevents generic stale writes restoring support.
- **Ordinary backend writes:** prefer rejecting an existing-row support mismatch and requiring callers to reread/retry their narrow mutation. This is easier to reason about than silently preserving one field of an otherwise stale object. Redaction is an explicit exception that clears support. Move old-row read, append-only validation and write under one SQLite transaction, with equivalent MemoryBackend locking; merely moving the SELECT under a connection-local Python lock is insufficient. Test confirm/retract/redact vs reassess on two connections.
- **Generations/snapshot:** approve authoritative-row non-ignored→ignored increment, idempotent repeated ignore and no decrease on reopen. All state writers must respect IGNORED and explicit reopen, including stale consolidation. Tracked head and metadata must be read with the episode in one snapshot, validated against canonical correspondence; original archive stays usable, SUMMARY never substitutes. Projection maintenance must cover UPSERT/delete/replace behavior and fail closed on corruption. The proposed reusable low-level source snapshot seam is appropriate; do not pull M2c rendering changes into it.
- **Resolver coverage:** approve support checks for every SelfModel ancestor, actual-provider localness and ceiling on each validation, scoped Agent forwarding, context/history/current cards and prospective-preview isolation. Fix the design's function name: current constructor path is `_build_agent`, not `_agent_fuer`. Supplied Agent wiring must use coherent explicitly supplied stores; do not quietly pair an Agent with unrelated default stores. No resolver is not proof of no episode linkage. Recognized typed/producer/orphan support fails closed; direct user records retain their existing semantics, and parent-only inference needs a successful lookup proving absence of linkage.
- **Historical basis:** stable complete privacy-safe withdrawn support may qualify a decision without asserting renewed source permission. Incomplete/missing/protected support withholds the descendant. Version3 history is warranted; v2 cannot certify support it never tracked. Reopened source with a changed generation requires a new explicit preview, never retrieval backfill.
- **Reassessment:** approve clean409 replay semantics, single-use token bound to full root, producer/evidence, all source generations/head/metadata, ancestry and scope. Prospective support override applies only to the selected root; it must not certify legacy parents. Age-outdated ACTIVE roots retain their original date/qualification. No confirm/record/reopen path is reused.
- **UI:** approve dedicated app/kingfisher memory subsection, independent of graph-fetch success, every bounded original quote visible before confirmation, explicit factual date, and truly read-only ProfileSource mode suppressing both handlers/buttons. Require actual synthetic browser/API/fake-provider acceptance, including stale token and external-provider switch; build alone does not prove this flow.

## Scope / handoff

This is a coherent but materially larger patch than M1c. Keep migrations, authorization-aware acceptance, validation and UI on one nondeployed branch until the vertical slice passes; do not deploy generation initialization alone. Existing backups/keys/restore images remain unchanged. Source deletion, restore quarantine/journals and arbitrary raw-database forgery are not solved by this authorization boundary. The design is ready for handoff once the three required corrections are made explicit; no model experiment is needed to implement or verify them.
