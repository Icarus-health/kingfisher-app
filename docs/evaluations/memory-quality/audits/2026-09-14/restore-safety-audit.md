# CHG-05/06 restore safety audit

Reviewed immutable `ed39aa02de8ee873520342531de70e97b6166bd9`; production was not edited. Relevant modules and the launcher were extracted with `git archive` into `/tmp/kingfisher-memory-work/restore-audit-ed39aa0` so concurrent M2b changes do not affect the proof.

## Concrete findings

1. **Restored originals and permissions immediately regain operational authority.** `recovery_bundle.py:49–94` verifies/decrypts a snapshot and restores its configuration without a restore-state marker. `scripts/open_restored_app.py:34–74` copies it into a separate writable volume, supplies the saved environment, and starts a normally networked container with `unless-stopped`. Only the copy helper uses `--network none`. Reopening an existing saved container also simply starts it. `server.py:979–990` loads secrets/settings and calls `_build_agent`; `_build_agent:685–731` constructs connectors/MCP/provider and `_wire_scheduler:846–852` starts the restored enabled schedule. Scheduler first run becomes due after its 30-second tick, without a new user action. With restored model processing enabled, consolidation/summary/task detection can use restored sources; restored mail/world/source settings can resume intake. Interactive chat, conversation chat, digest generation and direct tools also have no restore gate. Source-chain validation correctly rejects current ignored evidence but cannot infer a later revocation absent from the old snapshot. A coherent older claim/evidence/history fingerprint is not proof of current consent.

2. **In-place restore bypasses the same boundary, including legacy self-model backups.** `server.py:3964–4036` closes/replaces/reopens stores; `_reopen_persistent_state:873–910` loads old settings/secrets and calls `_build_agent`, which can restart workers before the restore request returns. Single-file restore rebuilds the Agent without quarantine too. `backup.py:274,413` preserves earlier files and verifies integrity, but does not reconcile decisions against the preserved newer state. Full snapshots include `regeln.sqlite3`, so a rule revoked after the snapshot can again match in `Agent._handle_call` (`agent.py:612–630`) and lower the policy level for a new call. This is a renewed-authority path, **not evidence that completed external actions automatically replay**. Pending in-memory policy approvals are not proven to replay. The requirement still needs an explicit unresolved-execution boundary before future action use.

3. **A safe in-place transition requires actual quiescence.** `server.py:3986–3999` comments promise no concurrent requests, but the route does not take a shared operation barrier. `Scheduler.stop()` (`scheduler.py:268–280`) joins for five seconds and may return while its worker lives; `run_once` executes successive jobs without a restore generation guard. Closing stores is therefore not proof that old operations have drained. A quarantine gate must be established before closing/replacing stores and checked by already-running work before provider/tool/sink use and result acceptance. A new HTTP-only guard would miss these in-flight paths. This conclusion is from code inspection, not a real concurrent restore execution.

## Smallest staged fix

1. **Introduce explicit restore quarantine as runtime state, not a source status rewrite.** Every successful restore target gets a versioned pending restore record containing a fresh restore/generation ID, snapshot identity and reason. Write it in staging before exposing the target. The trusted launcher must create/enforce it even when an old image performed extraction. For in-place restore, establish pending transition state outside the overwritten snapshot set before mutation. Preserve existing active app, original restored folder, backups, encrypted keys, image selection and rollback copies. Do not change all sources to ignored or overwrite users' saved settings to simulate quarantine.
2. **Boot a guarded inspection mode before constructing integrations or starting workers.** Load restore state before `create_app` builds providers/connectors/MCP or calls `_wire_scheduler`. Offer a persistent, clearly labelled historical snapshot view and status/recovery/export controls. Do not call models even locally, ingest, classify, summarize, create derived data, contact connectors, honor restored permanent rules, or execute tools/actions while pending. Separate user-visible read-only inspection from model retrieval: reading old data for explicit recovery inspection is not granting it operational authority. Use a central runtime gate plus a small explicit safe-route allowlist; some GET routes/connectors can have side effects, so HTTP method alone is insufficient. Apply the gate also at Agent/provider/tool/sink and worker entry/commit boundaries, not just UI routes. Include `person_digest_api.py`'s direct `complete_json` and manual `/ingest`, `/consolidate`, `/summaries/run`, `/schedule/run`, `/tools/{name}`, approval and conversation routes.
3. **Handle unsupported old images explicitly.** Passing a new environment flag to an old image does not enforce it. Preserve the image and recovered data but do not launch an unguarded normal app under a quarantine label. Provide an inspection-capable compatible runtime or a clear unsupported-mode recovery screen/export path. A host-enforced offline container alone is not sufficient: old code can still transform data, and reopening an existing `app.json` must not bypass capability/state checks. Do not silently stop or change the user's existing primary app or an already-running old restored instance; show the explicit transition required.
4. **Separate review from activation.** If a newer trusted local state exists, stage reconciliation of revocations/source permissions and action outcomes using it; never replace it with the older snapshot first. If it is lost, show that later decisions are unknown. Activation is a fresh explicit decision for this restore and permitted source/integration scope, not a claim that lost deletions were recovered. Keep automatic workers, restored permanent rules and unresolved external execution candidates disabled until separately reviewed. Old approval IDs must not become activation authority. Preserve pending state across restart, crash, repeated restore and copied restore targets; snapshot content must not be able to carry an activation authorization into a new restore. Full deletion-journal semantics and backup erasure remain separate design work.

## Exact implementation surface and acceptance tests

Primary: `sidecar/icarus_memory/recovery_bundle.py`, `backup.py`, `server.py`, `agent.py`, `scheduler.py`; `scripts/restore_recovery_bundle.py`, `scripts/open_restored_app.py`; direct model routes including `person_digest_api.py`. Add a shared restore-state/gate module, explicit status/activation API and visible recovery mode UI. Existing `recovery_jobs.py` is a backup coordination store, not restore authorization. Integration callers must use the same gate rather than unrelated ad hoc flags.

Required synthetic regressions: the proof above stays blocked operationally after restore; source revocation, assertion retraction, permanent-rule revocation and changed provider/source permissions after snapshot; full bundle/full local snapshot/legacy self-model restore; no provider/MCP/connector construction or scheduler start before guard; chat/conversation/digest/manual worker/direct tool/approval attempts blocked; previously running worker and held provider/tool result cannot cross generation; failed restore recovers original working state with no premature worker restart; pending state survives restart/reopen and cannot be cleared by old config/environment/backup data; unsupported old image remains recoverable without normal execution; keys/original files/images remain intact; explicit historical reads work without model use. Use fake providers/sinks and blocking events to prove zero calls, not only a displayed read-only badge. Later activation tests must distinguish newly authorized scopes from unknown historical decisions and must show no external action replay.

Verdict: current restore is recoverable and integrity-checked, but does not satisfy default CHG-06 read-only or CHG-05 prevention of reappearance. Implement the staged boundary first; it cannot by itself certify complete deletion reconciliation.
